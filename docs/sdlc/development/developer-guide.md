<!-- sdlc:auto:start overview -->
PMS23 is a performance management system generated by the Quorq AI SDLC platform. It is split into two independently runnable apps in one repo: a Vite + React 19 single-page frontend containing the approved, reviewed screens (currently rendering seeded sample data, not yet wired to the API), and a FastAPI 0.115 backend that is still a scaffold — it exposes only a `/health` endpoint plus stub routers that will be filled in as architecture is approved. The backend defaults to a local SQLite database (auto-created on startup) so it runs without any external services, while `docker-compose.yml` provisions Postgres and Redis for when the real architecture is implemented.
<!-- sdlc:auto:end overview -->

<!-- sdlc:auto:start prerequisites -->
- Node.js (for npm/Vite/React 19, see frontend/package.json)
- Python 3.12 (per backend/Dockerfile)
- pip
- Docker and Docker Compose (optional, for Postgres/Redis via docker-compose.yml)
<!-- sdlc:auto:end prerequisites -->

<!-- sdlc:auto:start setup -->
1. Clone the repository
2. cd backend && pip install -r requirements.txt
3. cd frontend && npm install
4. (optional) docker compose up -d to start Postgres/Redis if the backend's DATABASE_URL is pointed at them
5. cd backend && uvicorn app.main:app --reload (starts the API on http://localhost:8000)
6. cd frontend && npm run dev (starts the SPA on the Vite dev server, default http://localhost:5173)
<!-- sdlc:auto:end setup -->

<!-- sdlc:auto:start conventions -->
- Backend organizes endpoints into one router per architecture component under backend/app/routers
- Unimplemented routes return a typed StubResponse (schemas.py) rather than failing, keeping the OpenAPI doc complete
- All SQLAlchemy models inherit from the shared Base declared in app/database.py
- Backend uses a request-scoped DB session via the get_db dependency, one session per request
- Frontend screens live one-module-per-screen (per frontend/README.md), with shared UI/icon vocabulary in src/lib/ui.tsx and src/lib/icons.tsx
- Frontend API access is centralized in src/lib/api.ts (apiFetch), which attaches a bearer token (session token or shared secret) to every call
- Frontend component tests sit beside the components they test and are matched by Vitest's src/**/*.{test,spec}.{ts,tsx} pattern; Playwright specs live separately in e2e/
- Formatting/linting enforced via ESLint + Prettier (frontend) and ruff (backend)
<!-- sdlc:auto:end conventions -->

<!-- sdlc:auto:start troubleshooting -->
| Problem | Solution |
|---|---|
| Frontend calls to the API are blocked by CORS | Set the backend's ALLOWED_ORIGINS env var to a comma-separated list including the frontend's origin; it defaults to the Vite dev server origins (http://localhost:5173, http://127.0.0.1:5173) |
| Backend fails to start when DATABASE_URL points at a database server | Ensure the target database (e.g. Postgres via docker compose up -d db) is running and reachable; tables are only created at startup via Base.metadata.create_all, not via migrations |
| docker compose up fails or two services conflict on port 6379 | Both redis-queue and redis services map to host port 6379 in docker-compose.yml; only one can bind that port at a time, so adjust the port mapping for one of them before starting both |
| npm run test:e2e fails to start the backend webServer | Playwright's local run expects a Python venv at backend/.venv with dependencies installed (per playwright.config.ts); create it and install backend/requirements.txt there, or set E2E_BASE_URL to point at an already-running deployment |
| npm run build succeeds but the app doesn't actually typecheck | Run npm run typecheck (tsc --noEmit) separately, since npm run build does not perform type checking |
<!-- sdlc:auto:end troubleshooting -->
